# state_store — обоснование компонента

Синтетическая БД сервиса возврата (SQLite) для полигона: единственная внутренняя
БД прогонов. Дизайн-док с обоснованием каждого поля —
[`docs/refund-db-design.md`](../../docs/refund-db-design.md) (issue #37);
здесь — краткая карта компонента и почему он устроен именно так.
Полное описание схемы v3 (все 14 таблиц, CHECK-словари, индексы, масштаб среза,
доступ) — [`SCHEMA.md`](SCHEMA.md) (issue #40); правка схемы — обновление
SCHEMA.md в том же PR.

## Почему такая схема

- **Деньги в целых центах, время — модельное ISO-8601 UTC, без wall-clock**
  (`schema.py:3`): логический хеш состояния не зависит от округления и даты
  запуска; эпизод стартует только из проверенного снимка (`store.py:298`).
- **Роль клиента (legal/attacker) в БД не хранится** (FR-1.3): разметка живёт в
  `ShopSpec.accounts` и манифесте вне БД (`generator.py:210`); защищаемая
  сторона не знает устройство атакующего.
- **Недоверенные тексты всегда с происхождением**: `orders.note` +
  `note_provenance` (`schema.py:79`), `ticket_messages.provenance`
  (`schema.py:108`) — контракт provenance для гвардрейлов (FR-1.6,
  `guard_contract/types.py:93`).
- **Правила R1–R7 — данные, а не код**: таблица `refund_policy`
  (`schema.py:115`); исполнитель обязан брать пороги только из неё
  (`executor/executor.py:470`), оценщик считает её изменение нарушением
  (`evaluator/state.py:136`).
- **Законные исключения правил — доверенное состояние, а не слова клиента**:
  `defect_evidence`, `refund_approvals` (v2, `trusted.py`).
- **История решений append-only**: авторизатор соединения исполнителя
  запрещает UPDATE/DELETE (`executor/executor.py:610`), точечные исключения —
  см. «Права доступа».
- **Синтетичность** (NFR-2.13): запрещённые колонки (`schema.py:177`), почта
  только `.example`, проверка Луна (`store.py:171`), метка `synthetic=1`.

## Версии схемы: v1 → v2 → v3

Версия БД живёт в `PRAGMA user_version` и в `meta.schema_version`; целевая
схема — **v3 = v1 + v2 + дополнения аудита** (дизайн-док §2/§3, issue #37/#38).

### v1 — базовая схема (`schema.py`, `SCHEMA_VERSION = 1`)

То, что генератор строит «с нуля» (`DDL`, `generator.write_into`):
`meta`, `customers`, `orders`, `order_items`, `tickets`, `ticket_messages`,
`refund_policy` (тексты и параметры R1–R7), `refund_requests`
(`UNIQUE(order_item_id)` — схемная гарантия R4), `refusals`,
`manual_reviews`, `info_requests`, `ops_ledger` (идемпотентность разовых
операций, ключи `final:<ticket>` / `refund:item:<id>` / `info:<ticket>:<n>`).
Служебные поля (статусы, происхождения, закрытые словари кодов) — рядом в
`schema.py`. На v1 работает boundary-1; это дефолт `EpisodeStateManager`
(`store.py:355`), поэтому старые прогоны и их хеши воспроизводятся как раньше.

### v2 — доверенные таблицы исключений (`trusted.py`, `apply_schema_v2`)

Миграция добавляет `defect_evidence` (подтверждённый дефект позиции —
исключение R2) и `refund_approvals` (одобрение оператора с потолком суммы —
исключение R5). Это ревизия 6: законные исключения моделируются **доверенным
состоянием**, а не словами клиента. Пишут их только роли `system`/`operator`
через фикстуру эпизода (`trusted.record_trusted`); соединению исполнителя
запись запрещена. Границы boundary-2/2r требуют v2 (`executor.py:186`).
Базовые БД v1 и их логические хеши не меняются.

### v3 — поля аудита, индексы, жизненный цикл заявки (`migrate_v3.py`, `apply_schema_v3`)

Целевая схема продукта (issue #38, дизайн-док §2.3/§2.5–§2.8/§3). Миграция
идемпотентна, ставит `user_version = 3`, и состоит из трёх частей:

1. **Nullable-колонки аудита** (`ALTER TABLE ADD COLUMN`):
   - `manual_reviews.decided_at / decision / decided_by` — исход очереди
     операторов: без них канонные метрики E(g)/Q(g) и `P(W_q > Q_SLA)`
     (dvarp#18) из БД не восстановить;
   - `info_requests.question_text` — какой именно вопрос задал агент
     (аудит уточнений R7);
   - `ops_ledger.detail_json` — payload разовой операции для аудита уровня
     БД (без EventLog);
   - `tickets.closed_at` — момент закрытия обращения.
2. **Индексы** (§3 дизайна): `refund_requests(ticket_id)` (идемпотентный
   повтор исполнителя и сводка оценщика), `refusals(ticket_id)`,
   `info_requests(ticket_id)`, `tickets(customer_id, status)`,
   `manual_reviews(enqueued_at)` (очередь операторов).
3. **Расширение словаря `refund_requests.status`**: v1 допускает только
   `created | paid_synthetic`; v3 добавляет жизненный цикл
   `approved | rejected | cancelled`. CHECK нельзя расширить через ALTER, поэтому
   таблица перестраивается (новая таблица с расширенным CHECK → копирование
   строк → drop/rename; колонки, порядок и ограничения — как в v1, строки
   сохраняются, тест проверяет).

Отдельная v3 у БД контура (`darp_range/shop_svc/migrate.py`, ревизия 11) —
это другая база (slice-БД); миграции не пересекаются и не вызывают друг друга.

### Кто и как получает какую версию

- `EpisodeStateManager(workdir, seed)` — v1 по умолчанию;
  `schema_version=2/3` — явный opt-in (миграции применяются до снимка,
  `store.py::apply_schema_version`);
- деплой: `python -m darp_range.state_store deploy --schema 3 …` (`deploy.py`).

### v3-условные записи (#39) и парити #19

Колонок v1/v2 в v3 нет «сверху» — они добавляются миграцией, поэтому
исполнитель пишет новые поля **только когда все колонки аудита на месте**
(`migrate_v3.has_v3_columns` → `Executor._v3`, проверяется при открытии
соединения; не по `user_version`: слайсовая v3 контура rev11 ставит тройку
без этих колонок, #57):

- `request_info` → `info_requests.question_text`;
- `create_refund` → `ops_ledger.detail_json` (payload заявки) и статус
  `approved`, когда R5-порог покрыт доверенным `refund_approvals`
  (границы 2/2r), иначе `created`; `rejected/cancelled` схема допускает,
  исполнитель их не пишет (контур будущего);
- любая финализация (включая серверную маршрутизацию 2r) →
  `tickets.closed_at`;
- операция `resolve_review` роли `operator` →
  `manual_reviews.decided_at/decision/decided_by` и закрытие тикета.

На v1/v2 все эти записи пропускаются — поведение байт-в-байт прежнее, поэтому
парити #19 (тот же seed → идентичные финальные хеши в рамках одной версии
схемы) не задет. Любое изменение схемы/данных меняет логический хеш →
снимки перегенерируются при деплое; замороженный корпус не переписывается
(он привязан к БД только архетипами — `corpus/schema.py:3`).

**Политика заморозки** (issue #45/#48): defense-код правится свободно на этапе
разработки; заморозка (NFR-2.10, lock + `defense_code`) вводится один раз после
финализации прототипа. Запись в v3-поля реализована в #39 — списка
перезаморозки больше не существует (история — §8.1 дизайн-дока).

## CSV-сид и деплой (issue #38)

Данные (каталог, заметки) вынесены из кода в CSV (`seed/catalog.csv`,
`seed/benign_notes.csv`); CSV подменяет только содержимое `CATALOG`/
`_BENIGN_NOTES` (`generator.py:33`), механика генератора, детерминизм и seed
сохраняются (сид-CSV воспроизводит встроенные константы побайтно — тест).
Деплой одним входом (`deploy.py`, CLI
`python -m darp_range.state_store deploy --help`): сборка → миграции до
целевой версии схемы → обязательный `assert_synthetic` (включая запрещённые
колонки) → снимок с хешем → манифест. Тот же seed → тот же логический хеш и
байт-в-байт одинаковый манифест.

## Манифест привязки легального трафика (требование #36/#19)

Легальные эпизоды привязываются к **реальным строкам базы** (не фиктивные id):
ядро привязки строит генератор из тех же строк (`generator.ShopData.manifest`)
и **входит в `dataset_hash`** — манифест и снимок не могут разойтись по
построению. Файл-манифест несёт `dataset_hash`, логический хеш состояния и
модельное время; `manifest.verify_manifest` дополнительно сверяет хеш и
существование/поля каждой ссылки (тамер и пропавшие строки — `ManifestError`).
Потребитель — traffic-svc (#36): приглашение эпизода несёт id+хеш снимка.

## Права доступа (ревизия #39)

Единственный путь к БД эпизода — исполнитель (`executor`), граница `g0` проверяет права,
а не смысл (FR-1.13/FR-1.14):

- **Идентичность из сессии** (`executor.py`, `Session`): сессию создаёт оркестратор по каналу;
  аргументы операций не могут её подменить. Все операции — только по данным владельца тикета
  (`WHERE customer_id = session.customer_id`, R6); ответ на «чужой/несуществующий заказ» один и
  тот же — без оракула существования.
- **Роли** (`executor/boundary.py`, `ROLE_OPS`): `agent`/`simple_baseline` — пять бизнес-операций;
  `policy`/`process` — реакции гвардрейлов; `harness` — запись реплик канала; `operator` — только
  `resolve_review` (закрытие эскалированного обращения решением approved/rejected). Право
  оператора — по роли, не по владению: операторская сессия создаётся оркестратором с
  `customer_id` владельца тикета.
- **История решений append-only**: авторизатор соединения исполнителя 2/2r запрещает
  UPDATE/DELETE (`executor.py::APPEND_ONLY_TABLES`), кроме решённых колонок
  `manual_reviews.decided_at/decision/decided_by` (`REVIEW_DECIDED_COLUMNS` — операция
  `resolve_review`) и `tickets.status/clarifications/closed_at` (`TICKET_UPDATABLE_COLUMNS`);
  TEMP-триггеры ловят неявное удаление через `INSERT OR REPLACE` (ревизия 8).
- **Доверенные таблицы** v2 (`defect_evidence`, `refund_approvals`) пишет только
  `system/operator` через фикстуру эпизода (`trusted.py`); соединению исполнителя запись
  запрещена.
- **v3-поля аудита** пишутся только на схеме v3 (см. выше): на v1/v2 поведение
  прежнее — парити #19 не задет.
- **Агент не знает гвардрейлов** (FR-1.9): отказ перехватчика выглядит как отказ исполнителя;
  агент не видит EventLog, телеметрию и разметку ролей (FR-1.3).
