# state_store — обоснование компонента

Синтетическая БД сервиса возврата (SQLite) для полигона: единственная внутренняя
БД прогонов. Дизайн-док с обоснованием каждого поля —
[`docs/refund-db-design.md`](../../docs/refund-db-design.md) (issue #37);
здесь — краткая карта компонента и почему он устроен именно так.

## Почему такая схема

- **Деньги в целых центах, время — модельное ISO-8601 UTC, без wall-clock**
  (`schema.py:3`): логический хеш состояния не зависит от округления и даты
  запуска; эпизод стартует только из проверенного снимка (`store.py:298`).
- **Роль клиента (legal/attacker) в БД не хранится** (FR-1.3): разметка живёт в
  `ShopSpec.accounts` и манифесте вне БД (`generator.py:210`); защищаемая
  сторона не знает устройство атакующего.
- **Недоверенные тексты всегда с происхождением**: `orders.note` +
  `note_provenance` (`schema.py:79`), `ticket_messages.provenance`
  (`schema.py:108`) — контракт provenance для гвардрейлов (FR-1.6,
  `guard_contract/types.py:93`).
- **Правила R1–R7 — данные, а не код**: таблица `refund_policy`
  (`schema.py:115`); исполнитель обязан брать пороги только из неё
  (`executor/executor.py:470`), оценщик считает её изменение нарушением
  (`evaluator/state.py:136`).
- **Законные исключения правил — доверенное состояние, а не слова клиента**:
  `defect_evidence`, `refund_approvals` (v2, `trusted.py`).
- **История решений append-only**: авторизатор соединения исполнителя
  запрещает UPDATE/DELETE (`executor/executor.py:610`).
- **Схема v3** (`migrate_v3.py`): только nullable-колонки аудита, индексы и
  расширение словаря `refund_requests.status` — замороженный код продолжает
  работать; запись новых значений требует перезаморозки (список — §8.1
  дизайн-дока). БД v1/v2 и их хеши не меняются.
- **Синтетичность** (NFR-2.13): запрещённые колонки (`schema.py:177`), почта
  только `.example`, проверка Луна (`store.py:171`), метка `synthetic=1`.

## CSV-сид и деплой (issue #38)

Данные (каталог, заметки) вынесены из кода в CSV (`seed/catalog.csv`,
`seed/benign_notes.csv`); CSV подменяет только содержимое `CATALOG`/
`_BENIGN_NOTES` (`generator.py:33`), механика генератора, детерминизм и seed
сохраняются. Деплой одним входом (`deploy.py`, CLI
`python -m darp_range.state_store deploy --help`): сборка → миграции →
обязательный `assert_synthetic` → снимок с хешем → манифест.

## Манифест привязки легального трафика (требование #36/#19)

Легальные эпизоды привязываются к **реальным строкам базы** (не фиктивные id):
ядро привязки строит генератор из тех же строк и **входит в `dataset_hash`**
(`generator.ShopData.manifest`), поэтому манифест и снимок не могут
разойтись по построению. `manifest.verify_manifest` дополнительно сверяет
логический хеш и существование/поля каждой ссылки. Потребитель — traffic-svc
(#36): приглашение эпизода несёт id+хеш снимка.
