## 1. Сводка

- **Найдены остатки, которых нет у автора:**

  - затраты атакующего на композицию по-прежнему самоотчёт, до 1 ч на реплику;
  - замороженный список артефактов самоаттестован;
  - предрегистрация rev1 не проверяется вообще;
  - `Runner` и `report_cli live` в режиме A по умолчанию не используют sandbox, хотя одобренная задача этого требовала.

## 3. Где слабо (доказательство → последствия → серьёзность → условие устранения)

1. **Главная таблица v2r не даёт решения.**
   - Доказательство: `e2e/report.md` главного прогона. У всех 19 конфигураций на seed 7/8/9 `V=0`, ΔV=0,
     ДИ [−0.161; 0.161]. Статус формулы — `no_safety_gain`, итог — `unresolved`.
   - Приёмка допускает `unresolved` при ΔV=0, если причины записаны. Spec-сценарий
     «report lists them as no_safety_gain» буквально не выполнен: в столбце итога стоит `unresolved`.
   - Последствия: основа v2r на корпусе не ломается вообще, поэтому сравнение гвардрейлов
     структурно неинформативно — ΔV не может быть больше 0. Ширина ДИ ±0.16 говорит о малом n.
     Владелец процесса не получает `L*`. Это недостаток измерений (слабый для v2r корпус, малое n),
     а не ошибка расчёта.
   - Серьёзность: высокая для полезности полигона, нулевая для работоспособности.
   - Условие устранения:
     - атаки с паспортами, нацеленные на инварианты v2r, такие, что `V(g0) > 0` хотя бы на одном seed;
     - либо публиковать нижнюю границу `L*` по верхней границе ДИ ΔV: «даже при ΔV ≤ 0.16 окупается
       только при L_viol > X»;
     - в отчёте явно разделять «наблюдаемый no_safety_gain» и «unresolved».

2. **Нет тайм-аута IPC: зависший процесс атакующего вешает прогон.**
   - Доказательство: `_Proc.recv` вызывает `readline` без тайм-аута. Режим `hang` прерван внешним
     `timeout 90` (`logs/hostile2_hang.log`).
   - Последствия: враждебный или сломанный атакующий в будущей лиге останавливает весь прогон.
     Нарушение не превращается в `ipc_protocol_error`, хотя контракт ipc.py обещает обратное для
     любых нарушений.
   - Серьёзность: средняя для уровня C программы, низкая сейчас.
   - Условие устранения: тайм-аут на каждое ожидание ответа, например `select` с пределом из лимитов;
     истечение → `ipc_protocol_error` попытки и kill процесса. Тест с режимом `hang` должен давать
     `protocol_violation` за ≤ N с.

3. **Самоотчёт затрат атакующего не устранён полностью.**
   - Доказательство: `ipc.check_message` допускает `cpu_ms`/`latency_ms` в `message_composed` до
     3.6e6 мс, и мой `cpu_inflate` принят. Поля `data` событий атакующего свободны (`data_inject`).
   - Последствия: строка self-limited (NFR-2.9) раздувается атакующим до 1 ч на реплику. Затраты
     защиты и ΔNet не затронуты.
   - Серьёзность: низкая.
   - Условие устранения: брокер сам меряет время между отправкой observation и получением message.
     `data` событий — закрытая схема.
   - Связанная деталь: ложный `data.sent` должен давать `ipc_protocol_error`, а не провал
     приёмки «every attacker message reaches the defender». Это моё предположение по коду, сам
     прогон приёмки на этом режиме я не делал.

4. **Sandbox по умолчанию — только в одном скрипте.**
   - Доказательство: brief задачи claim-level требует AttackerFactory+bwrap по умолчанию для
     `live_mode_a_v.py` **и** для «runner с attack_strategy=llm, agent_mode=live». `Runner` без
     фабрики идёт in-process без ошибки (`logs/runner_live_a_default.log`). `report_cli`
     (`__main__.py`, `live.py`) фабрику не передаёт вообще.
   - Смягчение: манифест честно пишет `in_process_research`.
   - Последствия: живой A через основной CLI полигона не изолирован.
   - Серьёзность: средняя.
   - Условие устранения: `Runner` при `agent_mode=live` и `attack_strategy=llm` без фабрики и без
     явного флага → ошибка до первого запроса. Тест на фейковом транспорте — 0 запросов.

5. **Исторический контракт самоаттестован и неполон.**
   - Доказательство:
     - `historical_artifacts.sha256` лежит рядом со списком: подмена сводки rev8 с пересчётом обоих
       файлов проходит;
     - `preregistration-rev1.json` и записанные артефакты rev1 не проверяются никем;
     - `BEHAVIOURAL` — ручной перечень строк, не связанный с шагами verify программно.
       `closed_revisions.json: no_behavioural_check: []` — это утверждение, а не вычисление.
   - Последствия: защита от случайной правки есть, от намеренной — нет. Для rev1 «закрытой ревизии
     без проверки» фактически нет никакой проверки.
   - Серьёзность: низкая.
   - Условие устранения: внешняя фиксация sha256 списка; ниже записываю его для следующего прохода.
     Добавить rev1 в `PREREG`. Связать `BEHAVIOURAL` с именами шагов verify и проверять, что шаги
     существуют и PASS.
   - sha256 `historical_artifacts.json` на момент критики — см. `logs/historical_lock_sha.txt`.

6. **Регрессия legacy v1 ослаблена.**
   - Доказательство: spec требует побайтного равенства, автор сравнивает только стабильные столбцы
     (упрощение записано). Контроль шума `legacy_v1_noise_control.json` показывает 1928 различающихся
     ячеек затрат даже на одном коде.
   - Последствия: обоснованное упрощение, но spec не выполнен буквально.
   - Серьёзность: низкая.
   - Условие устранения: детерминированный учёт CPU офлайн (фиктивные часы заглушки) и после этого
     побайтное сравнение.

7. **Порог роста verify обойдён, а не соблюдён.**
   - Доказательство: план требовал при росте > 20 % сокращать legacy до seed 7. Автор запустил
     e2e параллельно: стена 3079 с, +10.5 %, но тот же объём работы последовательно (verify №1 автора) — +21.8 %.
   - Последствия: условие выполнено по букве и на машине с ≥ 2 ядрами.
   - Серьёзность: низкая (проверки не ослаблены).
   - Условие устранения: публиковать и CPU-время, и стену.

8. **Лексическая проверка текста `verify_e2e.py` осталась.**
   - Доказательство: `test_rev10_v2r.PrimaryFoundationTest` проверяет исходник регулярным выражением.
     verify №2 автора упал именно на ней и был починен новым регулярным выражением.
   - Смягчение: `primary_foundation` проверяет манифесты прогона поведенчески.
   - Серьёзность: низкая.
   - Условие устранения: удалить regex-проверки исходника и опираться на `primary_foundation`.

9. **Пробы проверяют launcher, а не процесс прогона.**
   - Доказательство: `broker_probes.run_broker_probes` запускает отдельный пробный процесс той же
     командой. Наблюдения sid/NSpid относятся к нему, а не к процессам атакующего в эпизодах.
   - Последствия: доказательство переносится на прогон только при неизменном argv. Брокер сверяет
     argv пробы с построенным (`host_argv_match`), но не argv каждого процесса атакующего.
   - Серьёзность: низкая.
   - Условие устранения: проверять `/proc/<pid>/cmdline` и NSpid каждого запущенного процесса
     атакующего.

10. **Защищаемая сторона по-прежнему видит атакующего** (FR-1.3, вторая половина).
    - Теперь это честно записано: `convention`, проба gc RED.
    - Серьёзность: средняя.
    - Условие устранения: отдельный процесс защиты.

## 4. Ремонт по кругу

- **Устранено.** Круг «правка общего кода → FAIL хеша закрытой ревизии → запись отклонения →
  verify заново» (D6.4, D7.3, D8.2, D8.6, D9.1, D9.2). За rev10 нет ни одного файла отклонений.
  Правка flow.py проходит, мой мутант исхода ловится. Бюджет учитывается пофайлово,
  `improvement-budget.json` не переписан.
- **Сохраняется.** Три полных verify на ревизию (rev6: 3, rev9: 3, rev10: 3), каждый ~50 мин.
  В rev10 причины другие:
  - №1 — порог времени;
  - №2 — лексический тест текста verify, починен другим regex (§3 п.8);
  - «найдено при интеграции» — отрицательные контроли ловили побочную ошибку отпечатка, а не
    проверяемое правило. Тот же класс дефекта, что «пустая проверка order scope» в rev8.

  Повторяется класс «тест проверяет не то» — его не ловят до полного verify. Нужен быстрый прогон
  мутантов для каждого нового отрицательного контроля до первого полного verify. `rev10_verify.py`
  — шаг в эту сторону.
- **Рост.** simplifications.json: 246 → 253 записи. verify: 108 шагов, но длительность растёт
  вместе с legacy-регрессиями.

## 5. Оценка по осям

- **Работоспособность — высокая.** Полный verify, быстрый verify, мутанты, OpenSpec и живой A через
  bwrap проходят в моих копиях.
- **Доказательность:**
  - **выше, чем в rev9** — для целостности трассы, чувствительности проб к флагам bwrap и проверок
    закрытых ревизий;
  - **низкая** — для устойчивости брокера к отказу ребёнка (тайм-аута нет);
  - **отсутствует** — для главного вопроса кейса: `L*` на v2r неопределён, живого `L*` нет.
- **Реалистичность:** v2r — разумная рекомендуемая основа; атакующий — код самого полигона, корпус не
  слепой. Отсутствие нарушений на v2r при атаках v1 ожидаемо: атаки писались против legacy-процесса.
- **Полезность:** инфраструктурная — честные метки, не ломающиеся исторические проверки. Для владельца
  процесса полезен отрицательный вывод «на этом корпусе v2r не ломается, и гвардрейлы ничего не
  добавляют», но отчёт подаёт его как `unresolved`.
- **Новизна:** нет — стандартная песочница и исторические контракты проверок.
- **Готовность к статье:** нет. Нет живого `L*` на v2r, нет слепого набора; изоляция применена в одном
  живом срезе (моём, n=1).

## 6. Классификация

- **Ошибки реализации:**
  - нет тайм-аута IPC (п.2);
  - самоотчёт cpu/latency и свободный `data` (п.3);
  - Runner/report_cli без sandbox по умолчанию (п.4);
  - rev1 вне контракта, самоаттестованный список (п.5).
- **Недостаток измерений:**
  - V=0 на v2r, малое n (п.1);
  - побайтная регрессия недостижима без детерминированных затрат (п.6).
- **Провал эксперимента:** нет.
- **Внешняя недоступность:** нет. bwrap 0.12.0, user namespaces и Qwen через прокси доступны.
