# Заявки на изменение канона

Канон исследования живёт в репозитории `CloudNative-urfu/dvarp`. Из задач
прототипа он **напрямую не редактируется** — вместо этого здесь создаётся
заявка на изменение.

## Структура

```
canon-requests/
├── README.md    # правила, шаблон, реестр
├── pending/     # заявки в работе: статус open (или rejected с причиной)
└── accepted/    # заявки, влитые в канон: есть PR в `dvarp`, статус accepted + ссылка
```

Заявка лежит в `accepted/` только когда правка канона реально смержена в
`dvarp` (файл не удаляется — остаётся как запись о принятом изменении).

## Правила

- Заявка создаётся **в том же PR**, что и изменение прототипа, которое её
  вызвало (в `pending/`).
- Имя файла: `NNN-<slug>.md` (сквозная нумерация, три цифры: `001`, `002`, …),
  slug — латиницей в kebab-case.
- Язык — русский; `path:line` обязательны (ссылки на код прототипа и на
  документы канона).
- Заявка не редактирует канон и не дублирует его текст целиком — только
  указывает, что устаревает и что предлагается.
- Принятие заявки — отдельным PR в `dvarp`; после мержа файл переносится в
  `accepted/`, статус обновляется ссылкой на PR.
- Если заявка отклонена — статус `rejected` с причиной; файл остаётся в
  `pending/`.

## Шаблон

```markdown
# NNN. <Краткое название изменения канона>

- **Дата:** YYYY-MM-DD
- **Источник:** issue/PR прототипа (ссылки)
- **Статус:** open | accepted | rejected (+ ссылка на PR в `dvarp`)

## Что сделано в прототипе

Кратко: что изменено и почему это затрагивает канон; ссылки `path:line`.

## Какой канон устаревает

Документ `dvarp` (путь), раздел, FR/NFR; что именно перестаёт
соответствовать.

## Предлагаемая правка

Формулировка (раздел/пункт), которую предлагается внести в канон; при
необходимости — запись в «Отклонения канона».

## Влияние

Какие задачи/документы/контракты затронуты; риски; что делать до принятия.
```
