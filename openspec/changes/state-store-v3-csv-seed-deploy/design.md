# Design: state-store v3, CSV seed and deploy manifest

Основание — дизайн-док `docs/refund-db-design.md` (issue #37): целевые
сущности и поля §2, индексы §3, данные агента §4, ground truth оценщика §5,
аудит §6, согласование с #19/#36 §7, расхождения §8, правки defense-кода §8.1.

## Ключевые решения

1. **Расширение, а не переписывание.** Базовый DDL v1 не меняется (контракт
   логических хешей #19): v3 — миграция по образцу `apply_schema_v2`
   (`trusted.py:34`), идемпотентная, `user_version=3`. Перестройка таблицы —
   только для `refund_requests` (расширение CHECK словаря статусов нельзя
   сделать через ALTER); колонки, порядок и ограничения — как в v1.
2. **Schema-only для новых значений.** В этом изменении появляются только
   схема и индексы; запись `decided_at/decision/decided_by`, `question_text`,
   `detail_json`, `closed_at` и новых статусов — правка defense-кода
   (§8.1, выполняется в #39). Тесты проверяют схему, не поведение
   записи.
3. **Манифест в `dataset_hash`.** Ядро привязки (accounts/orders → реальные
   id) строит генератор (`generator.ShopData.manifest`) и входит в
   `dataset_hash` — расхождение манифеста и снимка невозможно по
   построению; `verify_manifest` остаётся как внешняя проверка (хеш + поля
   каждой ссылки). Фиктивные id и плейсхолдеры исключены по построению.
4. **CSV-сид — только источник данных.** CSV подменяет `CATALOG`/
   `_BENIGN_NOTES`; состав входит в `dataset_hash` через строки; валидация
   сида — `SeedError` (уникальные sku, целые центы, ASCII).
5. **Не путать с v3 контура.** `shop_svc/migrate.py` (ревизия 11) мигрирует
   только slice-БД и не вызывает миграции эпизодных БД; направления
   независимы.

## Риски

- Изменение `dataset_hash` (манифест) меняет хеши базовых БД того же кода —
  снимки перегенерируются при деплое; дефолтный путь `EpisodeStateManager`
  и парити #19 не затронуты (v1 по умолчанию, та же версия кода → те же
  хеши).
- Замороженный корпус не трогается: привязка по архетипам
  (`corpus/schema.py:3`).
