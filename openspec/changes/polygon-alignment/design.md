## Context

The research claim (dvarp design §1): measure net gain and break-even L* for existing guardrail
configurations in the refund process with shared guardrail and queue capacity. The scaffold
implements the framework end to end (channel barrier, plugins, executor boundaries, queue,
evaluator-by-DB, metrics/L*, report_cli), but was generated by a factory campaign with its own
drift (17 configs, operator/payout contour, campaign bookkeeping — removed in issue #2).

## Goals / Non-Goals

- Goals: one maintained matrix covering 100% of the framework requirements; each gap becomes a
  board issue; scope decisions on factory extras are explicit.
- Non-Goals: implementing any gap in this change; reworking components; config re-freeze;
  touching frozen defense code.

## Decisions

- Decision: matrix lives in `docs/traceability.md` (team-facing), while the openspec change
  records the process and acceptance. The matrix is a living document: each follow-up change
  updates the rows it touches.
- Decision: statuses limited to four values; `covered-heavy` marks where simplification is
  possible but not scheduled (attacker isolation).
- Decision: the operator/payout contour (shop-svc/pay-emu/payout-worker) is kept for process
  realism and deferred — agreed with the issue author; revisit after the four gap issues close.
- Decision: follow-up issues get presumed assignees from the dvarp team table
  (infrastructure → geekiot-hub, config matrix → axstiz, case packs → BruhWhyMeHaveNoIdea,
  requirement gates → sser1to); the author may reassign.

## Risks / Trade-offs

- The matrix reflects the tree as of this change; without the discipline of updating it in each
  follow-up change it will rot. Mitigation: updating touched rows is part of every follow-up
  change's tasks.
- Verification references cite tests rather than fresh runs (full verify deferred per issue #2);
  the matrix will be re-validated by `scripts/verify.py` once models are wired and the pilot runs.

## Migration Plan

1. Land the matrix + change docs.
2. File the four gap issues on the board.
3. Execute follow-up changes issue by issue, updating the matrix.
