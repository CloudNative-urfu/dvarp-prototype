# Design: agent-db-verification-tool

Основание: дизайн-док `docs/refund-db-design.md` §4 (данные агента — разрывов
нет, только уточнения) и §8.1 (правки defense-кода, выполняются здесь);
канон-заявка `canon-requests/001-fr-1-11-db-verification-tool.md`.

## Ключевые решения

1. **Вариант 2 (расширение `read_order`), а не шестой тул.** Заявка 001
   разрешает реализацию поверх текущего набора до её принятия; число тулов
   остаётся 5 (FR-1.11 не меняется), оракула существования нет (чужой и
   несуществующий заказ — одинаковый отказ — не раскрываем). `purchase_history`
   отдаётся в каждом `read_order`: у агента нет способа перечислить заказы без
   id, поэтому без этого проверка «клиент реально покупал» невозможна в
   принципе. Объём на текущих данных мал (6 заказов на клиента).
2. **v3-условность записи.** Все новые поля пишутся только при наличии всех
   колонок аудита v3 (`migrate_v3.has_v3_columns`, а не `user_version >= 3`:
   слайсовая v3 контура rev11 ставит тройку без этих колонок, #57); на v1/v2 поведение байт-в-байт прежнее — парити #19
   (тот же seed → идентичные финальные хеши) сохраняется для старых схем.
3. **`resolve_review` — право по роли, не по владению.** Оператор не клиент:
   сессия оператора создаётся оркестратором с `customer_id` владельца тикета
   (проверка идентичности сохраняется), операция закрыта ролью `operator`.
   Тикет должен быть `escalated` с строкой `manual_reviews`; повторное
   разрешение — `ticket_not_open`. `approved` → `resolved`, `rejected` →
   `refused`.
4. **Статус `approved` у заявки** пишется исполнителем, когда R5-порог покрыт
   доверенным `refund_approvals` (границы 2/2r) — тогда в БД видно, что возврат
   прошёл по одобрению оператора. `rejected/cancelled` остаются для будущего
   небезопасного контура (схема допускает, исполнитель не пишет).
5. **`closed_at` пишет исполнитель** при финализации (все три решения +
   серверная маршрутизация + resolve_review); чтение из `ops_ledger` на стороне
   читателя — отклонённая альтернатива (defense-код правится свободно).
6. **Авторизатор: точечное исключение.** `manual_reviews` остаётся в
   `APPEND_ONLY_TABLES` (контракт rev7/rev8 не размывается); разрешается только
   UPDATE решённых колонок, TEMP-триггер на v3 прерывает любые прочие UPDATE
   этой таблицы (DELETE запрещён как раньше).

## Риски

- Отпечатки границ меняются (role_ops/описание авторизатора) — конфигурации
  `g` сверяют отпечаток по манифесту; текущий lock игнорируется на этапе
  разработки (#48/#52), перезаморозка не требуется.
- `purchase_history` увеличивает ответ `read_order` — на синтетике (6 заказов)
  незначительно; на больших данных потребуется пагинация (вне рамок).
