# Design

The orchestrator writes a launch file containing the plan, corpus entries, manifest,
snapshot path and stable snapshot id. No DB is generated by traffic-svc. Startup verifies
the snapshot metadata, logical hash and manifest references before publishing ready.json.
The service opens episode DBs read-only; the orchestrator applies the returned fixture
before defender-svc opens its executor. Ground truth is returned only to the harness.

`POST /flow` accepts the complete FlowInvite and uses its n_legal/blocks/mean_gap budget.
Existing `build_schedule` remains the common deterministic implementation: derived seeds,
Poisson arrivals, order and base/attacked filtering do not change. Service-mode execution
uses legal slots only; attack traffic is outside this service's binding contract.

`POST /bind` verifies the pristine restored hash, unchanged control and corpus index,
then binds using the manifest's accounts. Its response carries fixture, ground truth,
the corpus binding needed by the existing evaluator, and an opaque customer handle.
The handle is separate from evaluator data. Customer endpoints accept only Observation
fields and return text, completion and summary. They never accept telemetry or a defender.

One process serves a block. `run_flow` closes it; a reused adapter starts another process
for the next block and replays its invite. Unique process directories prevent stale ready
files across adapters/configurations. Exact last-request retries are cached under a lock;
changed bodies with the same request id are rejected. A second transport failure or a
non-200 stops the run and kills the process, without fallback to invented traffic.
Per-process requests.jsonl records repeated request ids. Transport does not enter parity.

SvcRunner caches EpisodeStateManager per config seed, loading repository CSV seeds once
when creating the baseline. Main-seed configs restore the same physical snapshot;
intentional seed-control configs get their own baseline. Existing snapshot metadata and
manifest remain the sources of binding truth. Cleanup runs on refusal and exceptions.

Defender HTTP handlers dispatch to a single worker thread under the existing lock.
This preserves both single-writer behavior and SQLite's connection thread affinity,
without weakening check_same_thread or changing defense code.

Windows verification also exposed existing snapshot test/cleanup assumptions: the WAL
regression now uses a crashed writer rather than an open handle; the permission test
closes its connection even on failure. Both runners remove their run-owned read-only
snapshots during temporary-tree cleanup, preserving other file permission bits.
