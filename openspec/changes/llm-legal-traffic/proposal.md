# Why

Issue #76: в живом прогоне легальный клиент должен имитировать реальный трафик возвратов —
LLM с промптом по фактам клиента и данным снимка, а не rule-based `ResponsiveUser`.
Scripted-клиент остаётся эталоном оффлайна (детерминизм, паритет in-process ↔ сервисы).

# What Changes

- Add `channel.LlmUser` — клиент за тем же `UserEndpoint`-протоколом: первая реплика из
  корпуса (детерминированный старт), далее — ответ модели по Observation агента;
  поведение и расходы (`usage`) — в `summary()` без текста реплик.
- traffic-svc строит клиента по launch-конфигу `client.kind = scripted | llm`
  (по умолчанию scripted — текущее поведение); для llm — режим модели `stub | live`
  (`RESEARCH_LLM_*`), отсутствие настроек живой модели — отказ до ready.json.
- `RunPlan.customer_mode` ("scripted" по умолчанию; в отпечатке — только если задан явно),
  флаг `runner svc --customer llm`; адаптер передаёт выбор в launch.json.
- Расходы LLM-клиента не входят в split accounting сторон (NFR-2.9): usage — данные
  события `legal_user`, пересчитываются движком позже; защитаемая сторона текстом
  клиента и его природой не располагает.

# Capabilities

- `legal-customer`: LLM-клиент легального трафика через существующий протокол клиента
  traffic-svc без изменения канала, защиты и метрик.

# Impact

Канал, защита, метрики и расписания не меняются. Новые файлы: `channel/llm_user.py`,
профиль заглушки клиента и фабрика клиента в `traffic_svc`. Оффлайн-прогон
(scripted) — побайтно прежний.
