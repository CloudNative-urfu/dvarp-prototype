# Ревизия 5 — план одобренных улучшений (стадия integrate, 2026-11-07)

Вход: `brief.md` (4 одобренные задачи), `improvement_darp_revision_5/{proposal/plan.json,
proposal/brainstorm.md, proposal/sources.md, review/review.md, review/independent-notes.md,
critique.md, case-update.md}`. Направление не меняется: дорабатывается существующий полигон.
Исторические входы (`revision*_input/`, `improvement_darp_revision_5/`, предрегистрации и locks
rev1–rev4, результаты прошлых прогонов) не изменяются; новое — в `artifacts/checks/revision5/`,
`artifacts/preregistration-rev5.json`, `runs/rev5_*`.

Порядок: report-validity → confirm-allowlist → confirm-impact → live-a-interleaved (офлайн-часть,
затем живые прогоны последними) → полный verify из чистой копии → документы.

## Задачи

### T1 `report-validity`
- Код: `metrics/frontier.py::pareto`, `metrics/robust.py::dominance` — допуск по стоимости
  `COST_EPS_USD = 1e-6` USD/эпизод (фиксируется в предрегистрации до прогона), стоимости в пределах
  ε равны; V/полезность — прежний `EPS`. `metrics/temporal.py` — `intervention_window_table`:
  IFR по k ∈ {0,1,2,3}, случайный базлайн, кластерный (по сценарию `entry_id`) bootstrap-ДИ
  разности IFR − IFR_rand; статус `informative` только если нижняя граница ДИ > 0, иначе
  `not_informative`. `rev4_stepshield_diag.py` → новый `scripts/rev5_window_table.py` (исторический
  скрипт не правится); report.md — таблица k=0..3, без утверждения по одному k=3.
- RED: тест `cost 1e-10 → равные` на старом коде падает (доминирование по шуму); синтетика с IFR
  ниже базлайна на старом коде не даёт `not_informative` (функции нет).
- GREEN/контроли: 1e-10 → не доминирует; 1e-3 → доминирование сохраняется (отрицательный
  контроль); синтетика ниже базлайна → `not_informative`; синтетика заметно выше → `informative`.
- Регрессия: фронт и список неэффективных seeds 7/8/9 совпадают с `revision4_verify`;
  `dominated_by` совпадает между двумя независимыми verify (сравнение двух каталогов).

### T2 `confirm-allowlist`
- Код: `darp_range/channel/proposal_contract.py` — позитивная грамматика «yes»: решение
  `consistent` только если КАЖДАЯ клауза сообщения сопоставлена одному из шаблонов:
  `proposal` (действие refund/return + ≥1 поле предмета ok: свой заказ / свой товар / сумма = цене
  или цене за единицу; допускаются только слоты шаблона: «to your original payment method/card»,
  «within N (business) days», вежливые модификаторы), `confirm_q` (закрытый список форм просьбы
  подтвердить), `courtesy` (целые клаузы из закрытого списка). Словарь NEUTRAL больше не даёт «yes»:
  клауза, не сопоставленная шаблону, → `incomplete` (уточнение). `slot_question` в сообщении с
  просьбой подтвердить — ответ на слот без «yes»; в вопросах кратность, третьи лица (вкл. them/they
  во фразе получателя) и надбавки → mismatch. Детектор противоречий (no) сохраняется.
- Разработка: восстановленные пробы критика rev4 (k01, k02, k04, k05, k06, k07, k19 — текст из
  critique.md §2; полный jsonl критика в рабочем каталоге отсутствует — упрощение) → no/clarify,
  RED на старом коде, GREEN на новом; позитивы c01/c02/c08/c17/c24 и восстановленные k20–k23 → yes;
  32 пробы и 12 вариантов rev3 — без изменений (тесты rev2–rev4); мутации rev4 12/12 и новая
  мутация «шаблон принимает любую клаузу» ломает тесты; генератор вставок слов бывшего NEUTRAL
  (them, they, less, below, under, all, away, send) в корректные предложения → 0 «yes».
- Независимое измерение: слепой набор (≥30 недопустимых, ≥30 корректных) пишет отдельная сессия
  (субагент Claude) без доступа к коду; каждая проба с меткой yes/no/clarify и обоснованием до
  оценки; SHA-256 набора — в предрегистрации rev5 до оценки. Публикуются ложные «yes» (Wilson95) и
  доля ложных уточнений при любом исходе; ложное «yes» записывается дефектом и в этом проходе не
  патчится. Авторство набора — Claude (та же семья моделей): независимость неполная.

### T3 `confirm-impact`
- Код: `scripts/rev5_confirm_impact.py` (офлайн). Источник — все живые журналы легальных
  эпизодов `ResponsiveUser` в рабочем каталоге (`runs/live`, `runs/live_fixed`,
  `runs/rev1/live_legal*`, `runs/rev1/live_mode_a`, `runs/rev2/live_slice`) с SHA-256 файлов.
  Для каждой живой конфигурации: N легальных эпизодов, доля с распознанным слотом confirm
  (фактическая — по событию `legal_user`; повторная — переоценкой текстов агента старым и новым
  контрактом), распределение confirm_yes/objection/clarify, task_status; худшие переворачивания
  (S1: все confirm_yes → lost; S2: все confirm_clarify → completed; S3/S4 — дополнительная, более
  строгая граница для R: confirm_yes → unjustified_refusal только у g или только у g0) с пересчётом
  ΔR, lost, режима bootstrap L* и состава Pareto-фронта; статический список путей «yes → изменение
  БД» по схеме `create_refund` и проверкам исполнителя.
- Правило (предрегистрация до запуска): если ни одно переворачивание не меняет режим L* и состав
  фронта ни в одной живой конфигурации → «деталь симулятора с ограниченным влиянием»; иначе
  результат T2 обязателен в оговорках живых R. «0/N, граница не измерима» допустимо.
- Отрицательный контроль: синтетический журнал с 50% confirm-эпизодов и разными исходами g/g0
  должен дать «режим L* меняется»; иначе скрипт признаётся нечувствительным (результат не
  публикуется как вывод).

### T4 `live-a-interleaved`
- Код: `scripts/live_mode_a_v.py` — `--interleave`: порядок по сценарию (atk-06/g0, atk-06/g_in, …),
  в run2 первым идёт g_in (`--first-config g_in`); у каждой ячейки (сценарий × конфигурация) свой
  счётчик (`--cell-budget`), общий лимит прогона сохраняется; статус измерения
  (`measured` / `truncated_*` / `not_measured_run_budget` / `not_measured_cell_budget`) пишется
  прямо в сырые строки `results.json`. Старое поведение (без флагов) сохранено для replay rev4.
- Лимит запросов на эпизод — по кассетам rev4 (фактическое число запросов atk-06/08/11),
  фиксируется в `preregistration-rev5.json` до живых запросов.
- RED (старый скрипт, фейковый бэкенд): исчерпание бюджета g0 уменьшает бюджет g_in; без попытки
  атакующего строка получает `ignored`. GREEN: у каждой из 6 ячеек свой бюджет; исчерпание g0 не
  трогает g_in; в сыром results.json — `not_measured_*`.
- Живые прогоны (последними): 2 × (3 сценария × 2 конфигурации × ≤10 запросов) ≤ 120; каждая
  ячейка измерена или помечена not_measured; replay кассет exact; публикуется описательно (n = 3).
- Регрессия: replay rev4 run1/run2 exact.
